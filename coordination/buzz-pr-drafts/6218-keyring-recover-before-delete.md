## Title

fix(desktop): don't delete corrupt keyring identity before a replacement exists

## Body

Fixes #6218.

`recover_from_keyring()` cleared the corrupt keyring entry unconditionally, before checking whether a valid `identity.key` fallback existed. When none did and the migration marker was present, the app correctly entered `Lost` recovery — but by then it had already destroyed the corrupt value with no chance of out-of-band recovery.

`store()` (a plain upsert) already overwrites the keyring entry once a verified replacement is written — either the migrated legacy file (via `migrate_identity_file`) or a freshly generated key (via `generate_and_persist`). So the explicit `delete()` was redundant in every path that finds a replacement, and actively destructive in the one path that doesn't. This removes it and lets entering `Lost` recovery leave the corrupt value in place instead, matching the issue's expected behavior ("only delete the corrupt value after successfully storing and verifying a replacement... preserve the corrupt value" when none exists).

Since nothing in this crate calls `IdentityKeyStore::delete` anymore, the trait method and its impls (and the now-pointless `deleted` spy bookkeeping in the test fake) are removed too — `SecretStore::delete` itself is untouched and still used elsewhere (e.g. agent keyring cleanup).

Added a regression test, `corrupt_keyring_marker_present_no_file_preserves_corrupt_value`, covering the issue's exact repro (corrupt keyring value + migration marker present + no fallback file): asserts `Lost` recovery is entered and the corrupt value is still readable in the keyring afterward. It fails against `main` and passes with this fix.
