## Title

fix(cli): don't reuse set's value-size limit for patch's diff input (#6262)

## Body

Fixes #6262.

`buzz mem patch` read stdin bounded by `NIP44_PLAINTEXT_MAX + 1` — the same limit `buzz mem set` uses for the *value* it writes. But `patch`'s stdin input is a unified diff, not the value — it carries both the old and new content plus hunk headers, so it can legitimately exceed that cap even when the patched result stays well under it. The read was silently truncated mid-hunk, and `diffy` then failed with a misleading "hunk header does not match hunk" parse error that gave no hint the real cause was a size limit rather than a malformed diff — exactly the issue's repro (a 71.9KB patch fails, a 64.7KB one succeeds, splitting the same content into two patches succeeds).

### Fix

Extracted the stdin read into `read_bounded_patch_input()`, bounded by a new `PATCH_INPUT_MAX` (4x the plaintext cap — generous enough for a full-content diff between two near-max-size values, still bounded against a wildly oversized input) and now returns an explicit `"patch input exceeds N-byte limit"` error on truncation instead of silently proceeding with a partial read. The patched *result* was already checked against `NIP44_PLAINTEXT_MAX` further down in `cmd_patch` and is unchanged — this only changes how much of the diff itself is read.

### Testing

Added two regression tests against the extracted helper:
- `read_bounded_patch_input_accepts_diff_larger_than_nip44_plaintext_max` — a diff sized in the exact range the issue reports failing (bigger than `NIP44_PLAINTEXT_MAX`, well under `PATCH_INPUT_MAX`); confirms it's no longer truncated.
- `read_bounded_patch_input_rejects_input_over_the_limit` — confirms input genuinely over the new limit gets the explicit size error rather than a silent truncation.
